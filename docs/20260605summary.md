## 二、代码仓库架构分析

### 2.1 七条关键链路

| 优先级 | 链路 | 路径 |
|--------|------|------|
| P0 | 偏差报告生成主工作流 | 前端 → IPC → XState → 4次LLM → 报告 |
| P0 | LLM 调用链路 | Provider配置 → Model创建 → Retry → Structured Output |
| P1 | RAG 知识库链路 | 文档 → 分块 → 向量化 → sqlite-vec → 检索 → 注入LLM |
| P1 | IPC 通信链路 | 6个模块桥接 Renderer ↔ Main Process |
| P2 | 数据持久化链路 | SQLite WAL + 3张表 (settings/reports/knowledge_docs) |
| P2 | AuditBee 集成链路 | 上传 → 创建任务 → 轮询 → 获取结果 |
| P3 | PDF 导出链路 | react-pdf渲染 → 文件写入 |

### 2.2 实际使用流程（优化前）

```
用户输入线索文本
  ↓
阶段1: 线索分析 (5-15秒) — 发送完整原文给LLM
  ↓
阶段2: 因素识别 (8-20秒) — 发送原文+analysis给LLM
  ↓
阶段3: 法规匹配 (5-30秒) — RAG检索 + 发送原文+factors+法规给LLM
  ↓
阶段4: 报告生成 (15-40秒) — 发送所有结果+Schema给LLM
  ↓
报告显示

总等待时间: 33-105秒（平均~60秒）
用户全程只能看进度条，无法操作
```

## 六、工作流性能优化（5项）

### 6.1 优化详情

| # | 优化项 | 修改前 | 修改后 | 收益 |
|---|--------|--------|--------|------|
| 1 | 阶段2+3并行 | 因素识别→RAG检索→法规匹配（串行） | 因素识别+RAG检索并行→法规匹配 | 节省5-15秒 |
| 2 | 流式输出 | `generateObject` 阻塞式 | `streamObject` 实时推送 | 用户实时看到报告生成 |
| 3 | 精简prompt | 用户原文在阶段1/2/3重复发送3次 | 阶段2/3用summary代替原文 | 减少~2000 tokens/次 |
| 4 | 预加载知识库 | 首次运行时加载（阻塞10-30秒） | 应用启动时后台加载 | 首次运行无额外等待 |
| 5 | 中间结果预览 | 只显示进度条 | 阶段1/2完成后展示分析结果 | 用户可感知进度 |

### 6.2 优化后流程

```
用户输入线索文本
  ↓
阶段1: 线索分析 (5-15秒)
  → 完成后立即展示: 偏差摘要、关键事件
  ↓
阶段2: 因素识别 + RAG检索 并行 (8-20秒，原13-50秒)
  → 完成后立即展示: 5M1E因素
  ↓
阶段3: 法规匹配 (2-5秒，原5-30秒，因RAG已预取)
  ↓
阶段4: 报告生成 流式输出 (15-40秒)
  → 实时展示报告内容生成过程
  ↓
报告完整显示

预计总等待时间: 30-80秒（原33-105秒），且用户全程可看到进展
```

## 九、项目当前状态

### 9.1 技术栈

- **桌面框架**: Electron 28
- **前端**: React 18 + TypeScript + Tailwind CSS 4
- **UI**: 自定义组件（precision laboratory 设计系统）
- **状态管理**: XState v5 状态机
- **LLM**: Vercel AI SDK（8个Provider: DeepSeek/通义千问/智谱/OpenAI/Anthropic/SiliconFlow/OpenRouter/Mimo）
- **RAG**: sqlite-vec + BAAI/bge-large-zh-v1.5
- **数据库**: better-sqlite3 (WAL模式)
- **动画**: gsap
- **路由**: React Router 6
